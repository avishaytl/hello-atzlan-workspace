# Hello Atzlan Workspace

HELLO ATZLAN — Complete Frontend UI/UX Design & Implementation Specification

1. Project Overview

Build a premium, production-quality desktop-first application called hello atzlan.

hello atzlan is a local-first AI developer workspace management platform designed to help software engineers manage multiple projects, Git worktrees, Claude Code sessions, development tasks, and IDE workspaces from one unified interface.

The long-term product will integrate with:

* Claude Code
* Git and Git Worktrees
* Jira
* Jenkins
* Mixpanel
* Statsig
* Contentful
* External IDEs such as VS Code, Cursor, and other compatible editors

However, this implementation is strictly frontend-only.

Do not implement backend services, Electron, authentication providers, real filesystem operations, Git commands, Claude CLI execution, or external API integrations.

Instead, build a complete interactive frontend with realistic mock data, simulated actions, and a clean architecture that will allow these integrations to be connected later.

The result must feel like a polished, native macOS application.

It should not look like a traditional SaaS admin template.

⸻

2. Product Vision

The central concept is:

One ticket. One workspace. One branch. One worktree. Multiple Claude sessions.

The application should eliminate the need for developers to manually remember:

* Which repository belongs to a task
* Which Git branch they were working on
* Where the worktree is located
* Which Claude session belongs to which task
* Whether Claude is currently running
* Which files were modified
* Which workspace needs attention
* How to reopen the correct IDE
* Where development was interrupted

The primary experience should revolve around quickly switching between isolated development workspaces.

A developer should be able to open the application, see all workspaces, select one, and immediately understand its state.

The UI must communicate clarity, control, productivity, and simplicity.

5. Technical Frontend Requirements

Use:

* React
* TypeScript with strict typing
* Vite
* Tailwind CSS
* shadcn/ui
* Radix UI primitives
* Lucide React icons
* React Router
* Zustand for lightweight client state
* TanStack Query for future asynchronous data integration

The project must remain compatible with a future Electron renderer.

Architecture Principles

Separate the UI from data access and platform-specific functionality.

Create distinct layers:

Presentation Layer

Reusable components, layouts, pages, dialogs, and visual states.

Application Layer

UI workflows, state coordination, navigation, filters, and action handlers.

Service Layer

Typed interfaces for workspaces, projects, Git, Claude, integrations, and IDE actions.

Mock Adapter Layer

Mock implementations of service interfaces using realistic local data.

Platform Adapter Boundary

A future integration point for Electron IPC.

The React UI must never directly depend on Node.js, filesystem APIs, shell commands, or Electron APIs.

Do not use Node.js APIs inside React components.

Use asynchronous service methods that can later be replaced with Electron-backed implementations.

For example:

interface WorkspaceService {
  list(): Promise<Workspace[]>;
  getById(id: string): Promise<Workspace>;
  create(input: CreateWorkspaceInput): Promise<Workspace>;
  archive(id: string): Promise<void>;
  openInIDE(id: string): Promise<ActionResult>;
}
interface ClaudeService {
  listSessions(workspaceId: string): Promise<ClaudeSession[]>;
  startSession(workspaceId: string): Promise<ActionResult>;
  resumeSession(sessionId: string): Promise<ActionResult>;
  stopSession(sessionId: string): Promise<ActionResult>;
}

Implement mock adapters that return realistic results.

Never call real external services.

Important

The application must be interactive and functional at the frontend level.

Buttons should not be decorative placeholders.

Actions should:

* Update mock application state when appropriate
* Show loading states
* Display success or error feedback
* Open relevant dialogs
* Navigate to the correct screen
* Simulate asynchronous operations

For actions that require a real backend, clearly label the behavior as simulated or preview-only.

Do not falsely indicate that an IDE, Claude process, Git operation, or external service was actually executed.

26. Electron Integration Readiness

The frontend will eventually run inside Electron.

Prepare the architecture accordingly.

Requirements

* No direct filesystem access in React components.
* No shell execution in the browser.
* No direct dependency on Electron APIs.
* No hardcoded absolute filesystem paths in application logic.
* No backend-specific implementation inside UI components.
* No assumption that external services are available.

Create typed service interfaces for all platform-dependent operations.

For future integration, allow a platform adapter to provide:

* Open IDE
* Open terminal
* Create Git worktree
* Remove Git worktree
* Start Claude
* Resume Claude
* Stop Claude
* Inspect process state
* Read Git status
* Read filesystem metadata

The current browser implementation should use mock adapters.

When Electron is added later, these adapters can be replaced with secure IPC implementations.

Security Considerations

Do not design an interface that requires disabling Electron security protections.

Future integration should support:

* Context isolation
* Sandboxed renderer
* Narrow typed IPC APIs
* Input validation
* No unrestricted shell command execution from UI
* No arbitrary filesystem access from the renderer
